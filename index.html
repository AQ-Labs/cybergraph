Why it exists

Agents generate code faster than anyone can review it.

Having the same class of model that wrote the code also review it is nondeterministic, spends tokens on every turn, and doesn't scale. Traditional scanners are noisy and flat — a file, a line, a rule — leaving the hard questions to you.

Questions on every change

Is this issue reachable from production code? Is there a login check before this sensitive action? Did this change move something across a trust boundary? Which findings matter first?

An answer, made independently

CyberGraph connects the dots and turns the answer into a decision made independently of the coding model — deterministic and local, cheap enough to run on every commit and every agent turn.

How verification works

Two verdicts — and it never turns “didn’t look” into a pass.

Every capability reports one of five explicit states, so a blind spot is visible, not silent. The distinctions between the last three carry the product's whole credibility.

PASS

The check ran on this change and found nothing.

FAIL

The check ran and found something.

NOT APPLICABLE

Supported, but nothing in this change is in its scope. Can honestly ACCEPT.

UNKNOWN

Supported, but it couldn't run here — a blind spot. Forces REVIEW.

NOT SUPPORTED

The capability doesn't exist yet for this language/surface. Forces REVIEW — accepting here would be false assurance.

A false ACCEPT is worse than a false positive. A capability passes only when there is positive evidence it was analyzed. A README-only change is NOT_APPLICABLE everywhere and can honestly ACCEPT; a change to a language with no analyzer is NOT_SUPPORTED and reviews — the two look alike and are not.
Compress complexity · never compress uncertainty

The wording never outruns the evidence.

Each finding is described only as strongly as it has been validated. The wording is bounded by the weaker of two axes — how strong the evidence is, and how mature the capability is for that language (effective_trust = min(evidence, assurance)).

Python · FastAPIBenchmark-backed
query = f"select * from users where name = '{name}'"
Confirmed: Unsafe database query
JavaScript · ExpressBeta
db.query(`select * from users where id = ${id}`)
Possible: Unsafe database query

Same tainted query. Different word — because the JavaScript verdict isn't held to a labelled benchmark yet, so its claim language stays bounded to “Possible.” No configuration, surface, or phrasing step can upgrade a reason above what its evidence supports. Uncertainty never becomes safety: when unsure, CyberGraph abstains and reviews, rather than issue a false ACCEPT.

The cardinal rule, in every language: only a provably all-literal construction can read SAFE. A value built from a variable is UNSAFE when taint confirms it, UNKNOWN otherwise; native deserialization is never SAFE. Anything the classifier can't read is UNKNOWN — never SAFE.
The knowledge graph

Not “a dangerous call exists.”
“User input can reach it — with no guard in between.”

CyberGraph parses your repo into a cybersecurity knowledge graph — routes, guards, validators, sinks, secrets, cloud resources, and the edges between them — then traces interprocedural attack paths from entrypoint to sink, each with confidence, taint, a risk score, and fix guidance.

reachability

Cross-file, interprocedural paths (route → service → repository → sink) with a --shallow mode for comparison.

resolution honesty

Cross-file call resolution degrades to low confidence · ambiguous rather than asserting certainty.

offline report

One self-contained HTML file: a neon graph explorer, security-zones view, and a guided top-attack-path narrative.

Automatic verification & the policy gate

Runs the moment code is accepted — enforcement kept separate from the verdict.

Install a hook and the verdict fires on every agent turn or commit, whether or not the agent chooses to check itself. A separate policy layer decides what CI does about a verdict — it never rewrites it.

block

A confirmed regression, or an unknown on a declared-protected route (by default). Stops the build.

warn

Surfaced, advisory. The change proceeds; the reviewer is told.

No policy can turn a REVIEW into an ACCEPT. The gate only decides whether CI stops; the verdict is reported unchanged beside it. --fail-on-review now fails the build only when the gate blocks.
# run automatically on every agent turn or commit
cybergraph hook install claude-code
cybergraph hook install pre-commit

# declare enforcement — cybergraph.policy.toml
[verification]
block_confirmed_regressions        = true
block_unknown_on_protected_routes  = true
block_general_unknown              = false

Get started

Zero API keys · zero signup · zero network calls.

Zero runtime dependencies and fully offline — installable in regulated environments where network-reaching tooling can't go. Python 3.10 – 3.13.

# install (isolated CLI)
pipx install cybergraph

# one command: verify a pending change,
# or scan the current code if there's none
cybergraph .

# the core verdict, machine-readable
cybergraph check . --json
# zero-to-report: init, build, analyze, open
cybergraph quickstart .

# interactive, offline HTML security map
cybergraph visualize path/to/repo

# evidence-cited answer, works with no LLM
cybergraph explain "Which routes reach SQL execution?"
